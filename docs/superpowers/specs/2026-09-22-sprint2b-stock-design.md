# Спринт 2, часть 2b: расходники, журнал движений, единая выдача — дизайн

## 1. Цель и объём

Часть 2b: расходники (позиции, приход, списание, корректировка, перемещение между складами), вкладка «История движений» — единый журнал операций с техникой и расходниками, единая форма «Выдать» для техники и расходников. Backend и frontend.

Принятые решения:

| Вопрос | Решение |
|---|---|
| Кто видит расходники и журнал | Только Admin; Employee и Manager не видят разделы и получают 403 от API |
| Склады | Позиция = наименование + склад (одна локация на позицию, как в ТЗ). Есть операция «Перемещение» между складами |
| Позиция на складе-получателе отсутствует | Создаётся автоматически при перемещении |
| Количество | Только целое |
| Возврат расходников от сотрудника | Отдельной операции нет; редкий случай оформляется «Приходом» с комментарием |
| Размещение кода | Внутри модуля `assets` (ТЗ 2.2: «оргтехника + расходники»), схема `equipment` |

Вне объёма 2b:

| Что | Когда |
|---|---|
| `StockMovement.ticket_id`, выдача по заявке, `TicketItem.fulfilled` | вместе с модулем заявок |
| Создание `Notification` при выдаче | спринт 4 (Telegram) |
| Дайджест и виджет «низкий остаток» | спринт 5 |
| Экспорт журнала и остатков | «Отчёты», спринты 5–6 |
| Возврат расходников как отдельная операция | не планируется |

## 2. Модель данных

Модуль `app/modules/assets`, новые файлы `stock_models.py`, `stock_operations.py`, `stock_router.py` и т. д. (файлы 2a не раздуваются). Схема `equipment`, миграция `0006_stock`.

### 2.1. `equipment.stock_items`

| Поле | Тип | Правила |
|---|---|---|
| id | bigint PK | |
| name | varchar(200) | обязательно, обрезается по краям, не пустое |
| stock_category_id | FK `common.stock_categories` | обязательно |
| unit | varchar(20) | обязательно, обрезается, не пустое («шт», «уп», «м») |
| location_id | FK `common.locations` | обязательно; после создания меняется только перемещением количества, не правкой |
| quantity | int | `CHECK (quantity >= 0)`, по умолчанию 0; меняется только движениями |
| min_quantity | int | `CHECK (min_quantity >= 0)`, по умолчанию 0 |
| is_active | bool | по умолчанию true; `CHECK (is_active OR quantity = 0)` |
| version | int | начинается с 1, растёт при правке и каждом движении |
| created_at, updated_at | timestamptz | |

Уникальный индекс `(lower(name), location_id)`. Индексы: `stock_category_id`, `location_id`.

«Низкий остаток»: `min_quantity > 0 AND quantity <= min_quantity`.

### 2.2. `equipment.stock_movements`

| Поле | Тип |
|---|---|
| id | bigint PK |
| stock_item_id | FK `equipment.stock_items`, индекс `(stock_item_id, id)` |
| movement_type | enum `stock_movement_type`: `receipt`, `issue`, `write_off`, `adjustment`, `transfer_out`, `transfer_in` |
| delta | int, `CHECK (delta <> 0)` |
| quantity_after | int, `CHECK (quantity_after >= 0)` |
| document_date | date null — только у `receipt` (`CHECK`: `movement_type = 'receipt'` ↔ `document_date IS NOT NULL`) |
| transfer_id | uuid null — общий для пары `transfer_out` / `transfer_in`; `CHECK`: заполнен ↔ тип `transfer_*`; индекс |
| reason_id | FK `common.issue_reasons` null |
| recipient_id | FK `common.users` null — `CHECK`: заполнен ↔ `movement_type = 'issue'` |
| comment | text null — `CHECK`: у `adjustment` не null |
| performed_by | FK `common.users` |
| created_at | timestamptz, индекс |

`CHECK` на знак: `receipt`, `transfer_in` — `delta > 0`; `issue`, `write_off`, `transfer_out` — `delta < 0`; `adjustment` — любой ненулевой.

**Две даты.** `created_at` — момент внесения в систему; по нему сортируются журнал и история, по нему выстраивается цепочка `quantity_after`. `document_date` — дата прихода по накладной (бизнес-дата), по умолчанию сегодня в часовом поясе компании, не в будущем; показывается отдельной колонкой. Проведение «задним числом» с пересчётом последующих остатков не делается.

Отступления от ТЗ 3.1: добавлены `is_active`, `version`, `transfer_id`, `document_date` (вместо поля «дата»), типы `transfer_out`/`transfer_in`, поле `user_id` названо `performed_by` (как в `asset_events`). `ticket_id` добавит миграция модуля заявок.

Каждое движение и каждое создание/правка позиции дополнительно пишутся в `common.audit_log`.

## 3. Операции с расходниками

Все операции — только Admin. Живут в `assets/stock_operations.py`.

| Операция | Движения | Поля запроса | Проверки |
|---|---|---|---|
| Создание позиции | — | name, stock_category_id, unit, location_id, min_quantity? | активные категория и склад; остаток 0 |
| Правка позиции | — | name?, stock_category_id?, unit?, min_quantity?, is_active?, `version` | склад не меняется; `is_active = false` при остатке > 0 → 409 `stock_not_empty` |
| `receipt` (приход) | `receipt` +N | quantity ≥ 1, document_date?, comment? | позиция активна; дата не в будущем |
| `write_off` (списание) | `write_off` −N | quantity ≥ 1, reason_id, comment? | N ≤ остатка; причина обязательна, `applicability` stock/both |
| `adjustment` (корректировка) | `adjustment` ±Δ | actual_quantity ≥ 0, comment (обязателен, не пустой) | Δ = actual − текущий под блокировкой; Δ = 0 → 422 `adjustment_no_change` |
| `transfer` (перемещение) | `transfer_out` −N, `transfer_in` +N, общий `transfer_id` | quantity ≥ 1, to_location_id, comment? | склад ≠ исходного, активен; N ≤ остатка |
| Выдача | `issue` −N | только в составе единой выдачи (п. 4) | N ≤ остатка |

Движение у неактивной позиции (кроме `transfer_in` в найденную неактивную позицию) — 409 `stock_item_inactive`.

**Перемещение.** Позиция на складе-получателе ищется по `(lower(name), to_location_id)`. Если нет — создаётся с тем же наименованием, категорией и единицей, `min_quantity = 0` (запись в `audit_log`). Если найдена неактивная — активируется. Обе позиции блокируются `SELECT … FOR UPDATE` в порядке id. Гонка двух перемещений, создающих одну позицию: нарушение уникального индекса перехватывается (savepoint), позиция перечитывается и блокируется.

**Корректировка через фактический остаток:** Admin вводит, сколько насчитал; сервер вычисляет Δ от остатка под блокировкой, поэтому изменения между открытием формы и отправкой не искажают результат.

**Конкурентный доступ.** Строка позиции блокируется `SELECT … FOR UPDATE`, остаток проверяется под блокировкой; недостаточно — 409 `insufficient_stock`, `details: {stock_item_id, requested, available}`. `CHECK (quantity >= 0)` — последняя линия защиты. Правка позиции — блокировка + сравнение `version`, расхождение — 409 `version_conflict`; правка без изменений не меняет `version`. Уникальность — 409 `stock_item_name_taken`. Пустое после обрезки наименование или единица — 422 `name_blank` / `unit_blank`.

**Проверки (422):** `category_invalid`, `location_invalid`, `reason_invalid`, `reason_required`, `document_date_in_future`, `same_location`, `comment_required`.

## 4. Единая выдача

`POST /api/equipment/checkout`, только Admin:

```json
{
  "recipient_id": 12,
  "asset_ids": [101, 102],
  "stock_lines": [{"stock_item_id": 7, "quantity": 2}],
  "reason_id": 3,
  "comment": "…"
}
```

- `asset_ids` — 0..50, `stock_lines` — 0..50; хотя бы одна строка всего, иначе 422 `checkout_empty`. Повтор позиции в `stock_lines` — 422 `duplicate_stock_line`; повтор актива — 422 `duplicate_asset`.
- Получатель: активный пользователь, иначе 422 `recipient_invalid`.
- Причина (необязательна): её `applicability` должна покрывать весь состав — только техника → assets/both; только расходники → stock/both; смешанный состав → both. Иначе 422 `reason_invalid`.
- Транзакция: блокируются активы (`ORDER BY id`), затем позиции (`ORDER BY id`). Собираются **все** проблемы: актив не найден или не `in_stock`; позиция не найдена, неактивна или остатка меньше запрошенного. Есть хотя бы одна — 409 `checkout_unavailable`, ничего не меняется:

```json
{"assets": [{"asset_id": 101, "inventory_number": "…", "status": "in_use"}],
 "stock": [{"stock_item_id": 7, "name": "…", "requested": 2, "available": 1}]}
```

- Иначе: активы → `in_use` с владельцем, событие `issued` (как в 2a); по каждой строке — движение `issue` с `recipient_id`. Причина и комментарий — во всех записях. Аудит — на каждое изменение.
- Код блокировки и выдачи активов переиспользуется из 2a. `POST /api/assets/issue` удаляется (выдача одного актива из карточки, `POST /api/assets/{id}/operations`, остаётся). `POST /api/assets/return` не меняется.

## 5. API расходников и журнала

Все запросы — только Admin, иначе 403 `insufficient_role`. Формат ответов и ошибок — как в спринте 1, списки — `Page[T]` с `limit`/`offset`.

| Запрос | Описание |
|---|---|
| `GET /api/stock-items` | Фильтры: `category_id`, `location_id`, `q` (≤ 100 символов, `ILIKE` по наименованию), `low_stock`, `include_inactive` (по умолчанию неактивные скрыты). Сортировка: наименование, затем склад |
| `GET /api/stock-items/{id}` | `StockItemRead`: поля + `category_name`, `location_name`, `is_low` |
| `POST /api/stock-items` | Создание |
| `PATCH /api/stock-items/{id}` | Правка (п. 3) |
| `POST /api/stock-items/{id}/operations` | Размеченное объединение по `operation`: `receipt`, `write_off`, `adjustment`, `transfer`. Ответ — обновлённая позиция |
| `GET /api/stock-items/{id}/movements` | `Page[StockMovementRead]`, новые сверху |
| `POST /api/equipment/checkout` | Единая выдача (п. 4) |
| `GET /api/equipment/movements` | Журнал (ниже) |

**Журнал.** Один SQL-запрос `UNION ALL` по `equipment.asset_events` и `equipment.stock_movements` (обе таблицы — модуля `assets`, межмодульного JOIN нет), приведённых к общим колонкам:

| Колонка | Техника | Расходники |
|---|---|---|
| kind | `asset` | `stock` |
| id, created_at | события | движения |
| operation | `event_type` (+ `operation` для `status_changed`) | `movement_type` |
| object_id, object_label | актив: инв. номер · модель | позиция: наименование |
| delta, quantity_after, unit | — | из движения и позиции |
| document_date | — | у прихода |
| from/to owner | `from_owner_id` / `to_owner_id` | — / `recipient_id` |
| from/to status | да | — |
| from/to location | да | склад позиции (у `transfer_out` — «откуда», у `transfer_in` — «куда») |
| reason, performed_by, comment | да | да |

Фильтры:
- `date_from`, `date_to` — даты в часовом поясе компании (`company_timezone`), включительно; переводятся в полуинтервал UTC;
- `kind`;
- `group` (повторяемый): `issue` (asset `issued` + stock `issue`), `return` (`returned`), `receipt`, `write_off` (оба вида), `adjustment`, `transfer` (asset `moved` + `transfer_*`), `status` (`status_changed`), `record` (`created`, `edited`);
- `person_id` — сотрудник в любом «владельческом» поле (`from_owner_id`, `to_owner_id`, `recipient_id`);
- `performed_by`;
- `location_id` — склад/локация «откуда» или «куда».

Сортировка `created_at DESC, kind, id DESC` — стабильна при совпадении времени. Перемещение расходника — две строки. Имена пользователей, причин, складов, категорий подставляются через `service.py` модулей `users_auth` и `directories` (функции из 2a).

## 6. Фронтенд

Фича `features/stock` (расходники, журнал); форма выдачи остаётся в `features/assets`. Меню «Склад и техника» у Admin: Техника · Расходники · История движений · Выдать / принять; у остальных — только «Техника». Маршруты расходников и журнала — под admin-гардом.

**Расходники** `/equipment/stock`: `DataTable` — наименование (ссылка на карточку), категория, склад, остаток + единица, минимум. Низкий остаток — строка подсвечена, остаток в `Chip` color="error". Фильтры в URL: категория, склад, поиск, «Только низкий остаток», «Показать неактивные». Кнопки «Добавить позицию» (`StockItemFormDialog`, после создания — карточка) и «Приход» (диалог с выбором позиции).

**Карточка** `/equipment/stock/:id`: шапка — наименование, склад, остаток, признак «низкий остаток» / «неактивна»; «Редактировать» и меню «Действия» (Приход / Списание / Корректировка / Перемещение). Один `StockOperationDialog` с полями по операции; у корректировки показывается текущий остаток и вычисляемое изменение. Вкладка «История» — движения позиции. 409 `insufficient_stock` / `stock_item_inactive` → уведомление «Остаток изменился — данные обновлены», перезагрузка. 409 `version_conflict` в правке — как в 2a.

**Выдать** `/equipment/issue`, блок «Выдать»: кому → техника (как в 2a) → расходники: строки «позиция + количество», «Добавить строку», удаление строки. Автокомплит — активные позиции с остатком > 0, подпись «Наименование · Склад · остаток N ед.», уже выбранные позиции исключены. Количество ≤ остатка проверяется на клиенте. Причина — список фильтруется по составу выдачи. 409 `checkout_unavailable` — форма остаётся, недоступные активы подсвечены, у строк расходников — «доступно N». Блок «Принять» не меняется.

**История движений** `/equipment/movements`: таблица — дата и время, операция, объект (ссылка на карточку актива или позиции), количество (±N ед.), кому/от кого, склад, причина, кто выполнил, комментарий; дата документа — во всплывающей подсказке у прихода. Фильтры в URL (п. 5).

Типы — из `openapi.json` (`make gen-api`), ошибки полей — `applyApiErrors`.

## 7. Тесты

Backend (pytest, реальный Postgres):
- все операции: знак `delta`, `quantity_after`, `version`, аудит; `CHECK` не даёт уйти в минус при прямом UPDATE;
- гонки в параллельных сессиях: две выдачи последних единиц — одна 409; встречные перемещения A→B и B→A — без deadlock; два перемещения, одновременно создающих позицию на складе-получателе;
- единая выдача: смешанный состав; один недоступный актив или нехватка по одной позиции — ничего не меняется, `details` перечисляет все проблемы; применимость причины; пустой запрос и дубликаты;
- корректировка: Δ, 422 при Δ = 0, обязательный комментарий;
- деактивация только при нулевом остатке; активация при перемещении в неактивную позицию; уникальность `(lower(name), location)`;
- журнал: объединение двух видов, каждый фильтр, границы периода в часовом поясе компании, порядок, пагинация;
- 403 для Employee и Manager на всех новых эндпоинтах; удалённый `POST /api/assets/issue` отвечает 405;
- миграция вверх и вниз, import-linter.

Frontend (Vitest + MSW): таблица и фильтры расходников, подсветка низкого остатка, диалоги операций (включая корректировку), строки расходников в форме выдачи и 409, фильтрация причин по составу, журнал и фильтры, пункты меню по ролям.

## 8. Ветка и порядок работ

Ветка `feature/sprint2b-stock` от `feature/sprint2a-assets`. Порядок: миграция и модели → операции с расходниками → API позиций → единая выдача (удаление `/api/assets/issue`) → журнал → фронтенд (расходники → карточка → форма выдачи → журнал) → README (пункты чек-листа ручной проверки с 14).

## 9. Критерии готовности

- `make test`, `make lint` (включая import-linter), `make frontend-check` зелёные; `openapi.json` и типы фронтенда актуальны.
- Остаток нигде не меняется в обход движений; не уходит в минус при параллельных операциях.
- Ручная проверка в браузере по чек-листу README: создание позиции, приход с датой документа, выдача техники и расходников одной операцией, списание, корректировка, перемещение на склад без такой позиции, конфликт двух вкладок, журнал с фильтрами, разделы скрыты у Employee и Manager.

## 10. Уточнения по итогам проверки реализации

Внесены при подготовке плана (`docs/superpowers/plans/2026-09-22-sprint2b-stock.md`), код которого прогнан целиком:

1. Блокирующие запросы позиций используют `populate_existing`: перемещение читает источник до блокировки, и без этого ORM вернул бы устаревший остаток (потерянное обновление при параллельных перемещениях).
2. Часовой пояс компании — `app/core/timezone.py` (`company_today`, `company_day_bounds`).
3. Журнал на фронтенде — отдельная фича `features/movements` (иначе цикл импортов `assets → stock → assets`).
4. Низкий остаток выделяется красным `Chip` остатка; строка таблицы целиком не подсвечивается (общий `DataTable` не меняется).
5. `StockMovementRead` дополнен `counterpart_location_id/name` — склад второй половины перемещения.
6. В журнале у движений расходников, кроме перемещений, `to_location` — склад позиции; у перемещения обе строки показывают «откуда → куда».
7. Список расходников сортируется по наименованию без учёта регистра, затем по id склада.
8. Страница «Выдать» переводится на `/api/equipment/checkout` вместе с удалением `/api/assets/issue`; строки расходников добавляются отдельной задачей.
9. Проверка причины — одна функция `check_reason(..., assets=, stock=)` для всех операций.
10. Уведомление об успешной выдаче — «Выдано позиций: N».
11. В журнале дата документа прихода показывается строкой в подробностях операции («Дата документа: …»), а не всплывающей подсказкой.
