## 1. Общие сведения

### 1.1. Цель проекта
Разработка внутреннего инструмента для IT-отдела компании: учёт оргтехники и расходников, трекинг служебных заявок от подачи до закрытия, Kanban-доска для управления задачами отдела.

### 1.2. Вводные

| Параметр | Значение |
|---|---|
| Размер команды разработки | 4–5+ человек с начала проекта |
| Число конечных пользователей | 10–15 сотрудников |
| Приоритет | Долгосрочная поддерживаемость и чистота кода — важнее скорости MVP |
| Инфраструктура на старте | Отсутствует (создаётся с нуля) |
| Внешние интеграции в MVP | Telegram-уведомления. AD/LDAP, Keycloak/SSO, 1С (онлайн) — не требуются в MVP |
| Данные по оргтехнике | Уже существуют в 1С в большом объёме — переносятся разовым импортом |
| Язык интерфейса | Русский |

### 1.3. Границы MVP
Входит: «Оргтехника» (включая учёт расходников по количеству), «Служебные заявки», «Kanban-доска», «Отчёты», Telegram-уведомления, разовый импорт данных из 1С.

Не входит в MVP (зона роста): AD/LDAP-авторизация, SSO/Keycloak, онлайн-интеграция с 1С, мобильное приложение, BI-аналитика, модуль «Кайдзен», email-уведомления.

## 2. Архитектура и стек технологий

### 2.1. Стек

### 2.2. Архитектурный паттерн — модульный монолит

Единый backend-проект со строгими границами между модулями:

```
app/
├── modules/
│   ├── assets/          # оргтехника + расходники (склад)
│   ├── tickets/         # служебные заявки
│   ├── kanban/          # доски, колонки, задачи
│   ├── notifications/   # Telegram-уведомления
│   ├── reports/         # агрегация и экспорт
│   ├── imports/         # разовый импорт из 1С
│   ├── directories/     # справочники, отделы, локации
│   └── users_auth/      # пользователи, роли, JWT
├── core/                # конфигурация, DB session, общая инфраструктура, audit
```

**Обязательное правило:** модули обращаются друг к другу только через сервисный слой (`service.py`), прямой импорт моделей другого модуля запрещён. Это защищает от «спагетти»-связности при параллельной работе нескольких разработчиков.

Правило проверяется автоматически: контракт `import-linter` в CI, нарушение блокирует merge. Код-ревью остаётся второй линией защиты, а не единственной.

**Внешние ключи между схемами.** Ограничения FK между схемами на уровне БД разрешены (например, `kanban.task.ticket_id → tickets.ticket.id`, любые ссылки на `common.users`) — целостность данных важнее чистоты изоляции при данном масштабе. Запрещено именно обращение к таблицам чужого модуля из кода. При будущей декомпозиции такие FK снимаются миграцией.

**Межсхемные JOIN** в основной бизнес-логике не используются; для отчётов разрешены через явные SQL-представления (views) в схеме `reporting`.

**Двусторонние связи модулей — доменные события.** Если двум модулям нужно реагировать на действия друг друга, прямая зависимость через `service.py` допускается только в одну сторону; обратное направление реализуется внутрипроцессными доменными событиями (`core/events.py`: регистрация обработчиков и синхронная публикация внутри текущей транзакции). Для пары `kanban` ↔ `tickets`:
- `kanban` зависит от `tickets` и вызывает `tickets.service` (проверка статуса заявки, закрытие заявки при переносе задачи в колонку `is_done`);
- `tickets` не импортирует `kanban`. При закрытии, отмене и отклонении заявки публикуются события `TicketClosed`, `TicketCancelled`, `TicketRejected`, на которые подписан `kanban`;
- обработчики идемпотентны: если связанная задача уже находится в колонке `is_done`, обработчик `TicketClosed` ничего не делает. Это исключает зацикливание «перенос задачи → закрытие заявки → перенос задачи»;
- исключение в обработчике откатывает всю транзакцию.

Направления зависимостей фиксируются контрактом import-linter (в частности, `tickets` не может импортировать `kanban`); циклические зависимости между модулями запрещены.

**Надёжность уведомлений.** Полноценный Transactional Outbox признан избыточным, но простой `after_commit`-хук теряет событие, если Redis недоступен в момент коммита. Поэтому:
1. Бизнес-операция в той же транзакции создаёт запись `Notification` со статусом `pending`.
2. `after_commit`-хук ставит Celery-задачу на отправку.
3. Периодическая задача (раз в 5 минут) досылает записи в `pending`, у которых `next_attempt_at` наступил более 5 минут назад, а также записи в `sending` с истёкшим `locked_until` (воркер упал во время отправки). Кандидаты выбираются через `SELECT … FOR UPDATE SKIP LOCKED`.

**Захват записи перед отправкой.** Проверки статуса недостаточно: задача из `after_commit` и досылка могут одновременно взять одну и ту же запись. Поэтому задача сначала атомарно захватывает запись условным обновлением:

```sql
UPDATE notifications.notification
SET status = 'sending', locked_until = now() + interval '2 minutes'
WHERE id = :id
  AND ((status = 'pending' AND next_attempt_at <= now())
       OR (status = 'sending' AND locked_until < now()))
```

Если строка не обновилась — запись уже обрабатывается другим воркером или отправлена, задача завершается. После ответа Telegram статус меняется на `sent` / `undeliverable`; при временной ошибке — обратно на `pending` с увеличением `attempts` и новым `next_attempt_at` (экспоненциальная задержка), после исчерпания попыток — `failed` (п. 4.6).

Гарантия доставки — «не менее одного раза»: если воркер упадёт между успешной отправкой в Telegram и фиксацией `sent`, возможен единичный дубль. Это допустимо.

### 2.3. Ролевая модель

| Роль | Права |
|---|---|
| Employee (сотрудник) | Создание своих заявок, просмотр своей техники, участие в Kanban (досках своего отдела и досках, куда добавлен) |
| Manager | Всё, что Employee + согласование заявок сотрудников своего отдела, создание Kanban-досок, просмотр отчётов по своему отделу, может быть исполнителем заявок |
| Admin | Полное управление реестром техники/склада, пользователями, отделами, справочниками, всеми заявками и отчётами, может быть исполнителем заявок |

**Область видимости.** Права проверяются на backend на двух уровнях: роль (доступ к операции) и объект (принадлежность записи). Employee видит только свои заявки и свою технику; Manager — данные своего отдела; Admin — всё.

**Кто согласует заявку.** Руководитель отдела автора (`Department.head_id`). Если автор сам руководитель отдела или руководитель не назначен — заявка уходит на согласование Admin: `approver_id` остаётся пустым, согласовать может любой Admin.

Согласующий фиксируется в `approver_id` при отправке на согласование. **При смене или снятии руководителя отдела** все заявки этого отдела в статусе «На согласовании», где согласующим был прежний руководитель, в той же транзакции переназначаются на нового руководителя; если руководитель не назначен или новый руководитель сам является автором заявки — на Admin (`approver_id` очищается). Изменение записывается в `AuditLog`, новому согласующему отправляется уведомление.

**Кто исполняет заявку.** Исполнитель назначается при согласовании. По умолчанию подставляется исполнитель из справочника типов заявок (`TicketType.default_assignee_id`), согласующий может заменить. Исполнителем может быть пользователь с ролью Manager или Admin.

Если исполнитель не назначен (тип не требует согласования и у него нет исполнителя по умолчанию), заявка в статусе «В работе» попадает в список «Нераспределённые», и исполнителя назначает Admin. Admin может сменить исполнителя заявки в статусе «В работе» или «На доработке» в любой момент (п. 4.3).

**Получатели системных алертов** (низкий остаток, истекающие гарантии, ежедневная сводка по просрочкам) — список пользователей, настраиваемый Admin в разделе администрирования. По умолчанию — все пользователи с ролью Admin.

### 2.4. Аутентификация и управление сессиями

- Пароли хранятся в виде хэша Argon2id (или bcrypt).
- Access-токен JWT — срок жизни 15 минут, передаётся в заголовке `Authorization`.
- Refresh-токен — срок жизни 14 дней, cookie с атрибутами `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/auth`; ротация при каждом использовании, хранится в БД (хэш) для возможности отзыва.
- Фронтенд и API обслуживаются с одного домена (API — по пути `/api` через реверс-прокси), поэтому cookie передаётся как first-party, а CORS в production не требуется (п. 7.3).
- Деактивация пользователя или смена пароля отзывает все его refresh-токены.
- Защита от перебора. Платформа доступна из интернета, поэтому блокировка не должна позволять постороннему запереть чужую учётную запись, зная только email:
  - не более 5 неудачных попыток за 15 минут для пары «учётная запись + IP-адрес», затем блокировка этой пары на 15 минут; вход в ту же учётную запись с других адресов не блокируется;
  - не более 20 неудачных попыток за 15 минут с одного IP-адреса по любым учётным записям, затем блокировка IP-адреса на 15 минут;
  - более 50 неудачных попыток за час на одну учётную запись со всех адресов — системный алерт получателям алертов (без автоматической блокировки);
  - счётчики хранятся в Redis; IP клиента берётся из `X-Forwarded-For` только если запрос пришёл от доверенного реверс-прокси;
  - Admin может снять блокировку вручную.
- **Сброс пароля** (email-сервиса в MVP нет): Admin выдаёт временный пароль, при первом входе смена обязательна. Дополнительно — сброс через Telegram-бота для пользователей с привязанным аккаунтом (одноразовая ссылка, срок жизни 15 минут).
- Первый Admin создаётся CLI-командой при развёртывании.

### 3.2. Правила целостности и конкурентного доступа

- **Остаток `StockItem`** не редактируется напрямую — меняется исключительно записью в `StockMovement` в одной транзакции. Перед изменением строка `StockItem` блокируется (`SELECT … FOR UPDATE`); `CHECK (quantity >= 0)` на уровне БД гарантирует, что остаток не уйдёт в минус даже при ошибке в коде.
- **Выдача актива** выполняется условным обновлением (`UPDATE … WHERE id = :id AND status = 'in_stock'`). Если строка не обновилась — актив уже выдан другим пользователем, API возвращает `409 Conflict`.
- **Переходы статусов заявки** выполняются с блокировкой строки заявки; повторный или устаревший переход отклоняется.
- **Редактирование** `Asset`, `Ticket`, `KanbanTask` — оптимистическая блокировка по полю `version`; при расхождении — `409 Conflict`, UI предлагает обновить данные.
- **Деактивация пользователя** с техникой «в работе», открытыми заявками (как исполнитель или согласующий) или ролью руководителя отдела требует предварительной передачи: UI показывает список и предлагает переназначить.
- Все даты и время хранятся в UTC (`timestamptz`), отображаются в часовом поясе компании (см. п. 7.6).

## 4. Навигация и логика по вкладкам

### 4.1. Дашборд
Персонализированная сводка: мои заявки, заявки на мне, мои задачи Kanban, моя техника, ближайшие дедлайны. Для manager/admin дополнительно: счётчик заявок на согласовании, просроченные заявки отдела; для admin — счётчик нераспределённых заявок. Для получателей системных алертов: позиции с низким остатком, техника с истекающей гарантией, активы в ремонте. Каждый виджет кликабелен и ведёт в соответствующий раздел с применённым фильтром.

### 4.2. Склад и техника

**Вкладки внутри раздела:**
- *Реестр техники* — таблица активов с фильтрами (статус, тип, владелец, локация, «требует проверки»), карточка актива (Информация / История / Связанные заявки).
- *Расходники* — таблица StockItem с остатками, визуальная подсветка позиций ниже минимального порога.
- *История движений* — единый хронологический журнал всех операций (выдача/возврат/приход/списание/корректировка, смены статусов техники) с фильтрами по датам, сотрудникам, типу операции.
- *Выдать / принять* — единая точка входа для изменения остатков и статусов (см. п. 4.2.1).

Операции изменения (выдача, приход, списание, смена статуса) доступны Admin. Employee и Manager видят реестр в пределах своей области видимости (п. 2.3).

**4.2.1. Логика выдачи (checkout) — selection-first**

Форма не содержит свободных текстовых полей для того, что уже существует как сущность в системе:
1. **Кому** — автокомплит по активным сотрудникам.
2. **Что** — для техники: список только активов со статусом «на складе»; для расходников: выбор позиции + числовое количество (не более текущего остатка). В одной операции можно выдать несколько позиций.
3. **Для чего** — выбор из справочника причин + опциональная привязка к существующей заявке в статусе «В работе». При привязке позиции заявки отмечаются как выполненные (`TicketItem.fulfilled`).
4. **Подтверждение** — одной транзакцией меняется статус/остаток, создаются записи `AssetEvent` / `StockMovement` и `Notification`; после коммита отправляется Telegram-уведомление получателю.

Если за время заполнения формы актив выдан кем-то другим или остатка уже не хватает — операция целиком отклоняется (`409`), UI показывает, какая позиция стала недоступна.

Возврат техники — зеркальное действие, статус актива меняется обратно на «на складе», владелец очищается.

Выдача по заявке не закрывает заявку автоматически — закрытие выполняет исполнитель (или перемещение связанной Kanban-задачи в колонку «Готово», п. 4.4).

**4.2.2. Статусы актива и допустимые переходы**

| Из статуса | В статус | Операция | Условие |
|---|---|---|---|
| — | На складе | Создание / импорт | — |
| На складе | В работе | Выдача | Указан владелец |
| На складе | Резерв | Резервирование | Опционально — привязка к заявке |
| Резерв | На складе | Снятие резерва | — |
| Резерв | В работе | Выдача | Указан владелец |
| В работе | На складе | Возврат | Владелец очищается |
| На складе, В работе, Резерв | В ремонте | Передача в ремонт | Владелец сохраняется (для возврата ему же) |
| В ремонте | В работе | Возврат из ремонта владельцу | Есть владелец |
| В ремонте | На складе | Возврат из ремонта на склад | Владелец очищается |
| На складе, В ремонте | Списана | Списание | Только Admin, обязательна причина. Финальный статус |

Переходы реализуются в сервисном слое; недопустимые блокируются backend независимо от UI. Каждый переход создаёт `AssetEvent`.

**4.2.3. Логика добавления**
- Поштучно — форма с валидацией уникальности серийного/инвентарного номера.
- Массово — импорт из Excel (см. раздел 6).
- Приход расходников — отдельная форма «Приход»: позиция + количество + дата + комментарий.
- Корректировка остатка (по итогам инвентаризации) — только Admin, обязательный комментарий.

**4.2.4. Мониторинг**
- Ежедневный дайджест получателям алертов: позиции с остатком ≤ минимального, техника с гарантией, истекающей в ближайшие 30 дней (п. 5.2).
- Виджеты на Дашборде: позиции с низким остатком, техника с истекающей гарантией, активы в ремонте.
- Активы без даты окончания гарантии в мониторинге гарантий не участвуют; их количество показывается отдельным счётчиком «гарантия не указана».

### 4.3. Заявки

Виды списка: Мои / На мне / На согласовании (manager/admin) / Нераспределённые (admin: заявки «В работе» без исполнителя) / Архив (финальные статусы).

**Типы заявок:** на выдачу техники, на расходники, на ремонт, прочая служебная записка — тип определяет состав полей формы создания и необходимость согласования (`TicketType.requires_approval`).

**Статусы:** Черновик, На согласовании, На доработке, В работе, Закрыта, Отклонена, Отменена. Финальные: Закрыта, Отклонена, Отменена.

**Таблица переходов (конечный автомат):**

| Из статуса | В статус | Кто выполняет | Условия / побочные эффекты |
|---|---|---|---|
| Черновик | На согласовании | Автор | Тип требует согласования. Назначается согласующий (п. 2.3) |
| Черновик | В работе | Автор | Тип не требует согласования. Исполнитель — по умолчанию из типа заявки, иначе исполнитель не назначается и заявка попадает в список «Нераспределённые» |
| Черновик | Отменена | Автор | — |
| На согласовании | В работе | Согласующий, Admin | Обязательно указан исполнитель. Фиксируется `approved_at` |
| На согласовании | На доработке | Согласующий, Admin | Обязательный комментарий |
| На согласовании | Отклонена | Согласующий, Admin | Обязательный комментарий |
| На согласовании | Отменена | Автор | — |
| На доработке | На согласовании | Автор | Тип требует согласования и заявка ещё не согласована (`approved_at` пуст) |
| На доработке | В работе | Автор | Тип не требует согласования либо заявка уже согласована (`approved_at` заполнен — возврат после запроса информации исполнителем). Повторное согласование не требуется; исполнитель сохраняется, если он не назначен — заявка попадает в «Нераспределённые» |
| На доработке | Отменена | Автор | — |
| В работе | Закрыта | Исполнитель, Admin; автоматически из Kanban (п. 4.4) | Фиксируется `closed_at` |
| В работе | На доработке | Исполнитель | Обязательный комментарий (не хватает информации от автора). Исполнитель и `approved_at` сохраняются |
| В работе | Отменена | Автор, Admin | Уведомление исполнителю. Выданная по заявке техника/расходники не возвращаются автоматически — исполнитель оформляет возврат отдельно |

Реализуется как явная state machine в сервисном слое; недопустимые переходы блокируются backend независимо от UI (`409 Conflict` с описанием причины). Каждый переход записывается в `TicketStatusHistory` и порождает Telegram-уведомление участникам (автор, согласующий, исполнитель — кроме того, кто выполнил переход).

**Действия без смены статуса:**

| Действие | В статусах | Кто выполняет | Условия / побочные эффекты |
|---|---|---|---|
| Назначение / смена исполнителя | В работе, На доработке | Admin | Исполнитель — пользователь с ролью Manager или Admin. Запись в `AuditLog`, уведомление новому и прежнему исполнителю |

Редактирование содержимого заявки (описание, позиции) доступно автору только в статусах «Черновик» и «На доработке». Если заявка уже согласована (`approved_at` заполнен), в статусе «На доработке» автор может менять описание, но не позиции: изменение состава запрошенного требует отмены заявки и создания новой, чтобы не обходить согласование.

**Мониторинг:** заявка считается просроченной, если дедлайн прошёл, а статус — «На согласовании», «На доработке» или «В работе». Черновики просроченными не считаются. Просроченные заявки подсвечиваются в списках, эскалируются (п. 5.1) и попадают в ежедневную сводку. Счётчик «На согласовании» виден manager в навигации без захода в список.

### 4.4. Kanban

- Список досок (карточки: название, владелец/отдел, число активных задач) → выбор → сама доска.
- Создание доски — manager/admin. Стандартный набор колонок: «Бэклог», «В работе», «На проверке», «Готово» (`is_done`). Колонки можно переименовывать, добавлять, удалять (кроме `is_done`) и менять порядок — если открытый вопрос 11.1 не будет решён иначе.
- Drag&drop с optimistic UI: визуальное изменение мгновенно, подтверждение — в фоне; при ошибке — откат карточки и уведомление с причиной.
- Порядок карточек в колонке хранится в поле `position`; перемещение — одним запросом (колонка + позиция).
- **WIP-лимит — мягкий:** при превышении колонка подсвечивается, перемещение не блокируется. На колонку `is_done` лимит не распространяется.
- Задачу можно создать из заявки (кнопка в карточке заявки) — создаётся связь `ticket_id`; у одной заявки не более одной задачи.
- Мониторинг: цветовая метка просрочки на карточках, сводка по нагрузке исполнителей.

**Синхронизация задачи и связанной заявки:**

| Событие | Статус заявки | Результат |
|---|---|---|
| Задача перемещена в колонку `is_done` | В работе | Сначала задача перемещается, затем в той же транзакции заявка переводится в «Закрыта» через сервис модуля `tickets` (с проверкой прав: переносящий должен иметь право закрыть заявку, иначе — `403` и откат) |
| Задача перемещена в колонку `is_done` | На согласовании / На доработке / Черновик | Перемещение отклоняется (`409`), UI откатывает карточку с сообщением «Связанная заявка ещё не в работе» |
| Задача перемещена в колонку `is_done` | Финальный статус | Перемещение выполняется, заявка не меняется |
| Задача перемещена из колонки `is_done` | Закрыта | Перемещение выполняется, заявка не переоткрывается (финальный статус) |
| Заявка закрыта из раздела «Заявки» | — | Связанная задача перемещается в колонку `is_done` своей доски (обработчик события `TicketClosed`, п. 2.2; если задача уже в `is_done` — без изменений) |
| Заявка отменена или отклонена | — | Задача остаётся на месте, на карточке появляется метка «Заявка отменена/отклонена» (обработчики событий `TicketCancelled` / `TicketRejected`) |

### 4.5. Отчёты

Read-only агрегация по существующим данным, без ручного ввода:
- **Техника:** распределение по типам/статусам/локациям, истекающие гарантии, активы без даты гарантии, активы «требует проверки» после импорта.
- **Заявки:** количество по статусам за период; среднее и медианное время закрытия (от `submitted_at` до `closed_at`, по заявкам, закрытым в периоде); среднее время согласования; просроченные.
- **Kanban:** нагрузка по исполнителям, просроченные задачи по доскам.
- **Выгрузка реестра для сверки с 1С** — в формате шаблона импорта (п. 6).

Экспорт каждого блока в Excel (.xlsx). Доступно manager (в пределах своего отдела) и admin (все данные). Отчётные запросы строятся на представлениях схемы `reporting`.

*Вне скоупа MVP:* кастомизируемые дашборды, сравнение периодов, автоматическая рассылка отчётов по расписанию.

### 4.6. Уведомления

- **Привязка Telegram-аккаунта:** пользователь нажимает «Привязать» в профиле → получает deep-link `t.me/<bot>?start=<code>` (одноразовый код, срок жизни 10 минут) → бот сохраняет `chat_id`. Отвязка — из профиля или командой `/stop` боту.
- **Настройка категорий** (чекбоксы): заявки — мои; заявки — на согласование; заявки — назначенные мне; выдача/возврат техники и расходников; Kanban — назначение задачи; системные алерты (только для получателей алертов). Уведомления о согласовании для согласующего по умолчанию включены.
- **История отправленных уведомлений** — у пользователя (свои) и у admin (все), с фильтром по статусу.
- **Недоставленные:** если Telegram-аккаунт не привязан — `skipped`; если бот заблокирован пользователем (ошибка 403 от Telegram) — `undeliverable`, привязка помечается неактивной. Admin видит список таких пользователей для диагностики.
- Временные ошибки Telegram API — до 5 повторов с экспоненциальной задержкой, затем `failed`. Между попытками запись возвращается в `pending` с новым `next_attempt_at` (п. 2.2).

### 4.7. Администрирование (только Admin)

- Управление пользователями и ролями: создание, выдача временного пароля, деактивация вместо удаления (с переназначением, п. 3.2).
- Управление отделами и их руководителями.
- Редактируемые справочники: типы техники, категории расходников, локации, причины выдачи, типы заявок (включая флаг «требует согласования» и исполнителя по умолчанию).
- Получатели системных алертов.
- Шаблоны текстов Telegram-уведомлений: редактирование с перечнем доступных переменных и предпросмотром; некорректный шаблон не сохраняется.
- Журнал действий (через общий `AuditLog`) с фильтрами по пользователю, сущности, периоду.
- Статус фоновых задач: последние запуски расписаний, очередь уведомлений, задачи импорта.

| Автоматизация | Триггер | Логика |
|---|---|---|
| Дайджест по складу и гарантиям | Ежедневно, 09:00 по времени компании (Celery Beat) | Одно сообщение каждому получателю алертов: StockItem с остатком ≤ минимального; Asset с `warranty_end_date` в ближайшие 30 дней или истёкшей за последние 7 дней. Позиции, впервые попавшие в список, помечаются «новое». Если список пуст — сообщение не отправляется |
| Эскалация просроченных заявок | Ежечасно | Ticket просрочена (п. 4.3) и `escalated_at IS NULL` → приоритет повышается на один уровень (не выше «критического»), заполняется `escalated_at`, уведомление исполнителю и согласующему. Повторная эскалация по тому же дедлайну не выполняется. При переносе дедлайна `escalated_at` сбрасывается; если заявка просрочит и новый дедлайн, она эскалируется снова (приоритет — ещё на уровень, не выше «критического») |
| Сводка по просроченным заявкам | Ежедневно, 09:00 | Одно сообщение: каждому исполнителю — его просроченные заявки; руководителю отдела — просроченные заявки отдела; получателям алертов — все |
| Уведомление о смене статуса заявки | Событие (переход state machine) | Уведомление автору/согласующему/исполнителю, кроме инициатора |
| Уведомление о выдаче/возврате | Событие (checkout / возврат) | Уведомление получателю |
| Автозакрытие заявки из Kanban | Перемещение связанной задачи в колонку `is_done` | По правилам п. 4.4 |
| Досылка зависших уведомлений | Каждые 5 минут | `Notification` в `pending` дольше 5 минут → повторная постановка в очередь (п. 2.2) |
| Очистка | Ежедневно, ночью | Удаление просроченных кодов привязки Telegram, отозванных refresh-токенов старше 30 дней, staging-данных импорта старше 30 дней |

### 5.2. Защита от повторов

- Все периодические задачи идемпотентны: повторный запуск в тот же период не создаёт дублей.
- Уведомления, которые не должны повторяться, имеют `dedup_key` (например, `digest:stock:2026-09-14:user:42`, `ticket:123:escalated:2026-09-14T15:00Z:user:42`); уникальный индекс не даёт создать вторую запись. Ключ всегда содержит получателя — иначе уведомление второму получателю того же события отбрасывается индексом. Ключ эскалации содержит дедлайн, по которому она выполнена, — иначе эскалация после переноса дедлайна была бы заблокирована.
- Для пометки «новое» в дайджесте хранится дата первого попадания позиции в список; при возврате остатка выше минимума или продлении гарантии отметка сбрасывается.

## 6. Разовый импорт данных из 1С

Поскольку в MVP не предусмотрена онлайн-интеграция с 1С, перенос существующего реестра техники выполняется разовым импортом.

**Данные, запрашиваемые у 1С-специалиста:** наименование/модель, серийный номер, инвентарный номер, дата принятия к учёту, материально ответственное лицо (МОЛ), местонахождение, (опционально) первоначальная стоимость, (опционально) дата окончания гарантии — если хранится в 1С или в отдельных документах.

**Процесс импорта:**
1. Скачивание шаблона Excel (.xlsx) со столбцами системы и листом с инструкцией.
2. Загрузка заполненного файла (только Admin).
3. Асинхронная обработка фоновой задачей (Celery) с индикатором прогресса — без блокировки интерфейса при больших объёмах. Строки сохраняются в staging (`ImportRow`), рабочие таблицы не затрагиваются.
4. Проверки:
   - обязательные поля и форматы (даты, числа);
   - дубликаты инвентарных/серийных номеров — внутри файла и с уже существующими в системе;
   - **сопоставление со справочниками:** система собирает уникальные значения типа техники и локации, не найденные в справочниках, и показывает их списком. Admin для каждого значения выбирает существующий элемент справочника или создаёт новый — сопоставление применяется ко всем строкам сразу;
   - **сопоставление МОЛ с пользователями** по нормализованному ФИО (регистр, «ё/е», порядок слов, инициалы). Неоднозначные и ненайденные значения — в список «требует ручной привязки».
   Проблемные строки не блокируют импорт остальных.
5. Отчёт перед подтверждением: сколько будет создано, сколько строк с ошибками, сколько требуют привязки; список ошибок можно скачать в Excel (исходные строки + колонка ошибки), исправить и загрузить повторно отдельным импортом.
6. Применение одной транзакцией после подтверждения:
   - актив с сопоставленным владельцем получает статус «В работе», без владельца — «На складе» с флагом `needs_review`;
   - для каждого актива создаётся `AssetEvent` типа «создание» с пометкой об импорте и ID задачи импорта;
   - список «требует ручной привязки» доступен в реестре через фильтр `needs_review`; флаг снимается при ручной привязке владельца или подтверждении статуса.
7. До применения задачу импорта можно отменить без последствий.

**Дата окончания гарантии.** Если в 1С её нет, поле остаётся пустым; такие активы не участвуют в мониторинге гарантий (п. 4.2.4). Для постепенного заполнения предусмотрено массовое редактирование даты гарантии в реестре (выбор нескольких активов → установка даты).

**Организационное следствие:** после импорта источником истины по оперативному статусу техники становится платформа, а не 1С. Регламент регистрации новой техники и периодичность сверки фиксируются до запуска (открытые вопросы 11.2, 11.3). Для сверки используется отчёт «Выгрузка реестра для сверки с 1С» (п. 4.5).

## 7. Нефункциональные требования

### 7.1. Резервное копирование
- Ежедневный `pg_dump` в 02:00; хранение 14 ежедневных и 8 еженедельных копий.
- Копии дополнительно отправляются за пределы VPS (другой сервер или S3-совместимое хранилище) — сбой единственного сервера не должен приводить к потере данных.
- Загруженные файлы импорта включаются в резервную копию.
- Проверка восстановления из копии — перед запуском в эксплуатацию и далее ежемесячно на staging.
- Целевые показатели: RPO — 24 часа, RTO — 4 часа.

### 7.2. Мониторинг и логирование
- Эндпоинты `/health` (приложение живо) и `/ready` (доступны БД и Redis); внешняя проверка доступности с оповещением в Telegram-чат команды.
- Сбор ошибок backend и frontend: Sentry или self-hosted GlitchTip.
- Структурированные логи в JSON с `request_id`; ротация логов Docker (ограничение размера).
- Алерты: заполнение диска > 80 %, неудачный бэкап, падение Celery worker/beat, рост очереди `pending`-уведомлений.

### 7.3. Безопасность
- HTTPS для всех соединений; HTTP перенаправляется на HTTPS.
- Секреты (ключ подписи JWT, токен бота, пароли БД) — в переменных окружения, не в репозитории.
- Фронтенд и API на одном домене (п. 2.4); CORS в production отключён, в локальной разработке разрешён только адрес dev-сервера фронтенда.
- Проверка прав на backend для каждого эндпоинта — на уровне роли и объекта (п. 2.3); права покрыты тестами.
- Загружаемые файлы: только .xlsx, ограничение размера (например, 20 МБ).
- Порты PostgreSQL и Redis не публикуются наружу.

### 7.4. Окружения и развёртывание
- Окружения: локальное (Docker Compose), staging, production. Staging может размещаться на отдельном небольшом VPS или на том же сервере в изолированном Compose-проекте.
- Деплой через CI: сборка образов → миграции Alembic → перезапуск сервисов. Откат — на предыдущий тег образа.
- Миграции обратно совместимы в пределах одного релиза (сначала расширение схемы, затем удаление старого — отдельным релизом).

### 7.5. Производительность
- Списки реестра, заявок и истории — серверная пагинация, фильтрация и сортировка.
- Целевое время ответа API — p95 < 500 мс при объёме до 20 000 активов и 50 000 записей истории.

### 7.6. Время и локализация
- Часовой пояс компании задаётся настройкой; расписания Celery Beat, «дни до окончания гарантии» и просрочка считаются в нём.
- Формат дат и чисел — российский.

## 8. План разработки (5 разработчиков, 9 недель, спринт = 1 неделя)

Каждый поток работ ведётся full-stack: разработчик(и) модуля делают и backend, и frontend своей части. Общие UI-компоненты (таблица с фильтрами и пагинацией, формы, автокомплит) создаются в спринте 1 и переиспользуются всеми.

| Спринт | Содержание |
|---|---|
| 1 | Скелет модульного монолита, import-linter, CI/CD, Docker Compose, staging. JWT-аутентификация (п. 2.4), пользователи, отделы, справочники. Скелет фронтенда, генерация типов из OpenAPI, базовые UI-компоненты. Проверка доступа к Telegram API с VPS |
| 2–3 | Параллельно: «Оргтехника» + расходники + статусы актива + выдача/возврат (2 разработчика); «Заявки» со state machine и позициями (2 разработчика); инфраструктура Celery/Redis + Kanban + список досок (1 разработчик) |
| 4 | Импорт из 1С (staging, сопоставление справочников и МОЛ, отчёт об ошибках). Telegram: привязка, отправка, надёжная доставка. Kanban: синхронизация с заявками |
| 5 | Все автоматизации (дайджесты, эскалация), настройки уведомлений, шаблоны. Дашборд. Начало «Отчётов» |
| 6 | Завершение «Отчётов» и экспорта, администрирование, AuditLog UI. Бэкапы, мониторинг |
| 7 | Интеграция модулей, сквозное тестирование (п. 9), пробный импорт реальной выгрузки из 1С на staging |
| 8 | Исправление ошибок, полировка UI, документация, проверка восстановления из бэкапа |
| 9 | Обучение пользователей, боевой импорт, запуск, буфер на непредвиденное |

**Если срок жёстко ограничен 7 неделями**, в зону роста переносятся (в порядке приоритета переноса):
1. Редактирование шаблонов уведомлений в UI (тексты остаются в коде).
2. Отчёт по Kanban и отчёт «Выгрузка для сверки с 1С».
3. Медианное время и время согласования в отчётах по заявкам.
4. Массовое редактирование дат гарантии.
5. Пометка «новое» в дайджестах.
6. Экран статуса фоновых задач в администрировании.

Бэкапы, мониторинг, проверки прав и защита от конкурентных изменений не переносятся.

## 9. Критерии готовности (Definition of Done)

- Код проходит линтинг, типизацию (mypy/pyright в CI) и проверку границ модулей (import-linter).
- Критическая бизнес-логика покрыта тестами: state machine заявок (все допустимые и недопустимые переходы), статусы активов, движения по складу (включая конкурентные операции), синхронизация Kanban ↔ заявка в обе стороны (включая отсутствие зацикливания), возврат с доработки согласованной заявки, переназначение согласующего при смене руководителя отдела, конкурентная отправка одного уведомления (запись захватывает ровно один воркер), защита от перебора паролей, проверки прав по ролям и объектам.
- API задокументировано в OpenAPI/Swagger; типы фронтенда сгенерированы из актуальной схемы.
- Миграции Alembic проходят отдельное код-ревью и имеют рабочий `downgrade`.
- Периодические задачи проверены на идемпотентность (повторный запуск не создаёт дублей; эскалация после переноса дедлайна срабатывает повторно).
- Функциональность проверена автоматизированным сквозным сценарием (Playwright): импорт техники → создание заявки → согласование → выдача → Kanban-задача → закрытие через перенос в «Готово» → отчёт.
- Перед запуском: успешное восстановление из резервной копии, пробный импорт реальных данных из 1С на staging.

## 10. Основные риски

| Риск | Комментарий |
|---|---|
| Расхождение данных между 1С и платформой после разового импорта | Требует организационного регламента сверки, не решается технически. Техническая поддержка — отчёт «Выгрузка для сверки» |
| Размытие границ модулей при параллельной работе 5 разработчиков | Митигируется автоматической проверкой import-linter в CI и код-ревью |
| Незамеченные ошибки импорта большого объёма техники | Митигируется staging-таблицей, предпросмотром, отчётом об ошибках и пробным импортом на staging |
| Низкое качество данных 1С (МОЛ текстом, нет гарантий, разнобой в названиях) | Митигируется сопоставлением справочников и МОЛ, флагом `needs_review`; объём ручной доработки оценить по пробной выгрузке в спринте 1–2 |
| Потеря данных при сбое единственного VPS | Митигируется внешними резервными копиями и регулярной проверкой восстановления (п. 7.1) |
| Недоступность Telegram API с сервера или блокировка бота пользователями | Проверка доступа в спринте 1; уведомления дублируются на Дашборде; admin видит недоставленные |
| Срок 9 недель окажется недостаточным | Заранее определён список переносимых функций (п. 8) |
| Bus factor при неполном покрытии документацией | Митигируется DoD-требованием к документации и cross-review |

## 11. Открытые вопросы к команде перед стартом

Для каждого вопроса указано значение по умолчанию, которое используется, если решение не принято к началу спринта 2.

1. **Состав Kanban-колонок** — единый стандарт для всех досок или свободная настройка каждым manager?
   *По умолчанию:* стандартный набор при создании, свободная настройка, колонка `is_done` обязательна.
2. **Регламент регистрации новой техники** после перехода на платформу — только платформа или дублирование в 1С для бухучёта?
   *По умолчанию:* бухучёт остаётся в 1С, оперативный учёт — в платформе; новая техника заводится в обеих системах с одинаковым инвентарным номером.
3. **Периодичность контрольной сверки** реестра техники с 1С.
   *По умолчанию:* ежеквартально.
4. **Итоговый список причин выдачи и типов заявок** для справочников (включая флаг «требует согласования» и исполнителя по умолчанию для каждого типа).
   *По умолчанию:* все типы требуют согласования, кроме «на ремонт».
5. **Кто исполняет заявки** — только Admin/Manager или нужна отдельная роль «IT-специалист» без прав администратора?
   *По умолчанию:* Manager и Admin (п. 2.3).
6. **Хранится ли в 1С дата окончания гарантии** и есть ли возможность выгрузить её вместе с реестром?
   *По умолчанию:* даты в 1С нет — поле остаётся пустым и заполняется постепенно массовым редактированием в реестре (п. 6).
7. **Требования к HTTPS-доступу** — платформа доступна из интернета или только из внутренней сети/VPN?
   *По умолчанию:* из интернета через HTTPS.
8. **Получатели системных алертов** — конкретные сотрудники.
   *По умолчанию:* все Admin.
