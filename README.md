# IT-платформа

Внутренний инструмент IT-отдела: учёт оргтехники, служебные заявки, Kanban. ТЗ — `docs/spec/TZ_IT_platforma_v1.2.md`.

## Требования

- Docker (OrbStack или Docker Desktop)
- [uv](https://docs.astral.sh/uv/)
- Node.js 24 (`.nvmrc` в `frontend/`)

## Запуск локально

```bash
make up                         # PostgreSQL и Redis
cp backend/.env.example backend/.env
cd backend && uv sync && cd ..
make migrate
make create-admin EMAIL=admin@company.ru NAME="Администратор"
cd backend && uv run uvicorn app.main:app --reload
```

API: http://localhost:8000/api/docs

## Проверки

```bash
make test      # тесты (нужны запущенные postgres и redis)
make lint      # ruff, mypy, границы модулей
make openapi   # после изменения API — обновить backend/openapi.json
```

## Развёртывание (staging/production)

Образ `backend/Dockerfile` по умолчанию запускается с `APP_ENV=production`. В этом режиме приложение не стартует, если:

- `JWT_SECRET` не задан или короче 32 символов;
- `COOKIE_SECURE=false` (refresh-cookie должна быть `Secure`);
- `CORS_ORIGINS` не пустой (фронтенд и API на одном домене);
- в `TRUSTED_PROXIES` есть некорректный адрес или сеть (проверяется в любом окружении).

### TRUSTED_PROXIES

IP клиента нужен для защиты от перебора паролей (блокировка по паре «учётная запись + IP» и по IP). Заголовок `X-Forwarded-For` учитывается только от адресов из `TRUSTED_PROXIES`.

- Формат — JSON-список адресов или сетей: `TRUSTED_PROXIES='["172.16.0.0/12"]'`.
- Список должен включать Docker-сеть, из которой обратный прокси (nginx и т. п.) обращается к backend.
- Прокси обязан перезаписывать `X-Forwarded-For` реальным адресом клиента или дописывать его в конец (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`).

Если прокси не указан в `TRUSTED_PROXIES`, все запросы выглядят как пришедшие с IP прокси: 20 неудачных входов любых пользователей за 15 минут заблокируют вход всем.

## Фронтенд

React + TypeScript (Vite), MUI в стиле шаблона Modernize. Код — `frontend/`.

```bash
make frontend-install
make frontend-dev      # http://localhost:5173, /api проксируется на localhost:8000
make frontend-check    # типы, ESLint, Prettier, тесты, актуальность типов API, сборка
make gen-api           # после изменения API: openapi.json + src/api/schema.d.ts
```

Весь стек в Docker: `docker compose up -d --build` → http://localhost:8080 (nginx отдаёт фронтенд и проксирует `/api`).

Если стек уже поднимался до появления фиксированной подсети (`172.28.0.0/16`), пересоздайте его: `docker compose down`, затем `docker compose up -d --build` (тома сохраняются). Иначе сеть останется со старой подсетью и `TRUSTED_PROXIES` не совпадёт с адресом nginx.

Первый администратор для Docker-стека создаётся с хоста: `make create-admin EMAIL=... NAME="..."` — команда запускается через uv и подключается к опубликованному порту postgres (`DATABASE_URL` с `localhost` в `backend/.env`).

### Ручная проверка перед релизом

Проверяется в браузере на http://localhost:8080:

1. Вход под администратором.
2. Перезагрузка страницы не разлогинивает.
3. Выдача временного пароля → вход этим пользователем → принудительная смена пароля.
4. Создание пользователя и копирование временного пароля (диалог закрывается только кнопкой «Готово»).
5. Деактивация руководителя отдела → показывается список причин блокировки.
6. Справочники: переключение вкладок, деактивация записи, «Показывать неактивные».
7. Выход в одной вкладке завершает сессию в другой.
8. Оргтехника: создание актива (типы и локации — из справочников), дубль инвентарного номера показывается под полем.
9. «Выдать / принять»: выдача нескольких активов сотруднику; приём части из них на склад с другой локацией.
10. Карточка: резерв → снятие резерва, ремонт → возврат владельцу, списание (без причины не проходит); история показывает каждый шаг.
11. Конфликт двух вкладок: одна выдаёт актив, вторая пытается зарезервировать его же → «Статус техники изменился», карточка обновилась.
12. Под сотрудником виден только свой реестр, под руководителем — техника отдела; «Выдать / принять» и «Действия» им недоступны.
13. Деактивация сотрудника с техникой «В работе» → в списке причин блокировки есть эта техника.

Структура `frontend/src`: `app/` (провайдеры, маршруты), `layout/` (каркас), `api/` (клиент и сгенерированные типы), `shared/ui`, `shared/lib`, `shared/lookups` (общие справочные запросы), `features/<модуль>/`. Фича импортирует другую фичу только через её `index.ts`; `api`, `theme` и `shared` не зависят от фич — это проверяет ESLint (`import/no-restricted-paths`).

## Фронтенд: обновление токена

Refresh-токен ротируется при каждом `POST /api/auth/refresh`. Фронтенд должен выполнять refresh в режиме single-flight: один запрос на вкладку (и координация между вкладками, например через `BroadcastChannel` или Web Locks), остальные ждут его результата. Повтор уже использованного токена в течение 30 секунд возвращает 401 без побочных эффектов; более поздний повтор считается кражей и отзывает все сессии пользователя. Реализация — `frontend/src/api/refresh.ts` (общий промис внутри вкладки и Web Locks между вкладками). Web Locks работают только в защищённом контексте (HTTPS или localhost); без них refresh синхронизируется только внутри вкладки.

## Оргтехника

Модуль `backend/app/modules/assets` (схема БД `equipment`), экраны — `frontend/src/features/assets`. Правила переходов статусов (п. 4.2.2 ТЗ) описаны одной таблицей в `assets/transitions.py`: из неё backend проверяет операции и отдаёт в карточке `allowed_operations`, по которым фронтенд строит меню «Действия». Статус, владелец и локация меняются только операциями (`POST /api/assets/{id}/operations`, массово — `/api/assets/issue` и `/api/assets/return`); `PATCH` меняет только описательные поля с проверкой `version`. Строки активов блокируются `SELECT … FOR UPDATE`, поэтому параллельная выдача одного актива даёт 409.

## Архитектура

Модульный монолит (`backend/app/modules/*`). Модуль используется другими модулями только через `service.py` и `events.py` — это проверяет `lint-imports` в CI. Обратные связи между модулями — через доменные события (`app/core/events.py`).
